# Great Expectations Live Demo

A 10-15 minute, four-command walkthrough of [Great Expectations](https://greatexpectations.io/) (GX) —
a Python tool for defining and checking data quality rules — against a small,
deliberately messy synthetic orders dataset.

## Before the talk: setup

Everyone following along should do this **before** the presentation starts, not during it.

```bash
git clone <this-repo-url>
cd <repo-folder>
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Requires Python 3.10–3.13. Verify your install:

```bash
python -c "import great_expectations as gx; print(gx.__version__)"
```

## During the talk: four commands

Run these in order. Each one builds on the last.

### 1. Look at the data

```bash
python 01_inspect_data.py
```

Prints a preview of `data/orders.csv` — 185 rows of synthetic e-commerce
orders. No Great Expectations here yet; the point is just to show that
nothing visibly screams "broken" when you skim it.

### 2. Define what "good data" means

```bash
python 02_build_expectation_suite.py
```

Creates a local GX project (`./gx`, gitignored — everyone builds their own)
and an **Expectation Suite**: ten named rules about the `orders` table,
e.g. "`order_id` is never null," "`item_price` is between $0 and $500."
Nine are straightforward rules; the tenth is a **statistical** check
(z-score) that flags prices that are technically inside the allowed range
but are still way outside the normal spread of order values — the kind of
anomaly a hard-coded threshold can't catch. Nothing is checked yet — this
step only declares the rules.

### 3. Validate — and see only that

```bash
python 03_validate_and_report.py
```

Runs the suite **once** against `data/orders.csv` and prints a colored
pass/fail table plus the statistical spotlight panel (the $410/$445
prices the range rule misses but the z-score check catches). This step
is deliberately bare: no Data Docs, no alerts, no files written. The
point is to show that validation by itself just hands you back a Python
result object — nothing else happens until you wire that result into a
Checkpoint.

### 4. Wire it into a Checkpoint and watch it act

```bash
python 04_run_checkpoint.py
```

Builds a `Checkpoint` around the **same** suite from step 2 — no rules
change — and attaches two Actions to it:

- A custom Action (`quarantine_action.py`) that splits the batch into
  clean and quarantined rows based on which rows actually failed an
  expectation, writes the bad ones to `data/quarantined_rows.csv`, and
  prints a pipeline-gate report ("BLOCKED" / "CLEARED"). This is real,
  not mocked — it writes an actual file, it just doesn't call a live
  Slack/PagerDuty webhook, so nothing here depends on credentials or
  network access during the talk.
- GX's built-in `UpdateDataDocsAction`, which builds the **Data Docs**
  HTML report and opens it in your browser.

This is the **Validate → Report → Act** arc your teammate's slides
introduce, made concrete: step 3 is Validate, step 4's Data Docs are
Report, and the quarantine panel is Act.

## What's actually in the data (presenter reference)

`data/orders.csv` is generated by `generate_data.py` (not run live — the
CSV is already committed so it's identical for everyone). It has 160 clean
rows and 25 rows seeded with specific, documented problems. Clean
`item_price` values are clustered tightly ($15-$85, a realistic typical
order value) specifically so the two "in-range but anomalous" rows stand
out statistically.

| Issue | Count | Expectation that catches it |
|---|---|---|
| `order_id` reused on a second row | 3 (→ 6 flagged rows) | uniqueness |
| `customer_email` is null | 3 | not-null |
| `customer_email` malformed (no `@`, double `@`) | 2 | regex match |
| `order_date` in the future | 2 | range (date) |
| `item_price` negative | 3 | range (numeric) |
| `item_price` over $500 | 3 | range (numeric) |
| `item_price` unusually high but still under $500 | 2 | **z-score only** — range rule misses these |
| `quantity` is 0 | 3 | range (numeric) |
| `shipping_country` not a real code | 2 | value in set |
| `status` not a real status | 2 | value in set |

Expect step 3's summary to show **1 of 10 expectations passing** — only
`order_id is never null` is clean. That's intentional: it makes for a
stronger demo than mostly-passing data. Step 3 also prints a callout
panel showing exactly which two prices (`410.0` and `445.0`) pass the
range rule but get caught by the z-score check — that's the moment to
pause and make the "statistical, not just rule-based" point.

Step 4's Act panel reports **28 quarantined rows**, not 25 — the 3 rows
with reused `order_id`s get both occurrences flagged (each one is
"unexpected" relative to the other), so that single issue contributes 6
flagged rows instead of 3. Worth knowing so it doesn't look like a bug if
someone in the audience does the arithmetic.

Step 4 is a direct, working version of the "Stop pipeline / Alert team /
Quarantine data" bullets and the "Build upon GX" diagram from your
teammate's slides — it's a good moment to explicitly call back to those.

## If something goes wrong live

- `ModuleNotFoundError` → the venv isn't activated, or `pip install -r requirements.txt` didn't finish. Re-run it.
- Steps 3 or 4 fail with "validation definition not found" → step 2 didn't complete successfully, or you're running from a different folder. Re-run step 2 first.
- Browser doesn't open automatically at the end of step 4 → open `gx/uncommitted/data_docs/local_site/index.html` manually.
- Want a clean slate → `rm -rf gx data/quarantined_rows.csv` and re-run steps 2 through 4.
